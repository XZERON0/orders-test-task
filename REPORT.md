# Отчёт по тестовому заданию — Orders

**Дата:** 12 ноября 2026 г.  
**Стек:** Node.js, Express, Prisma, PostgreSQL, Vitest / Supertest; Next.js, React, TanStack Query.

## Краткое резюме

Разобраны пять исходных дефектов (QA-101–QA-105). Основной акцент: корректность денежных расчётов, изоляция данных организаций, атомарное резервирование товара и согласованность интерфейса с сервером.

## QA-101 — Расхождение суммы строк и итога заказа

**Причина.** Сумма заказа рассчитывалась из общей неокруглённой стоимости со скидкой, тогда как каждая строка округлялась отдельно. Для трёх строк по 333,33 ₸ со скидкой 10% строки дают по 300,00 ₸, но расчёт скидки от общего subtotal даёт 899,99 ₸.

**Исправление.** Итог заказа рассчитывается как сумма уже округлённых `lineTotal`, с финальным округлением до двух знаков.

**Проверка.** Создать три отдельные позиции по 333,33 ₸, количество 1, скидка 10%; ожидать три строки по 300,00 ₸ и итог 900,00 ₸. Дополнительно проверить отсутствие скидки и количество больше единицы.

**Затронуто:** создание заказов, денежные итоги.

**Коммит:** `b5a6ac58f530d846bb37403a0178479b79d95f6e`.

## QA-102 — Доступ к заказам другой организации

**Причина.** Получение заказа по ID выполнялось без ограничения по `organizationId`, что позволяло прочитать чужой заказ по прямой ссылке (IDOR).

**Исправление.** Поиск заказа ограничен парой `id` + `organizationId` текущего авторизованного пользователя. Идентификатор организации передаётся в операции чтения и изменения статуса. Для чужого заказа возвращается `404`, без раскрытия его содержимого.

**Проверка.** Создать заказ от имени одной организации; убедиться, что владелец получает `200`, а пользователь другой организации — `404`. Проверить также запрет чужих операций `confirm`, `ship`, `cancel` и отсутствие побочных изменений.

**Затронуто:** просмотр заказа, подтверждение, отгрузка, отмена; разграничение доступа.

**Коммит:** `3fe1306e9cc011f46adf0ecc8099fa4cdb4e6440`.

## QA-103 — Подтверждение заказов сверх доступного остатка

**Причина.** Проверка учитывала только `onHand`, игнорируя `reserved`. Дополнительно чтение остатка и его изменение выполнялись раздельно, поэтому конкурентные запросы могли пройти проверку одновременно.

**Исправление.** Подтверждение выполняется в транзакции. Переход `DRAFT → CONFIRMED` проверяется условным обновлением. Резерв увеличивается атомарным SQL `UPDATE` только при условии `on_hand - reserved >= quantity`. Если условие не выполнено, возвращается `409`, транзакция откатывается.

**Проверка.** При остатке 1 создать два заказа по одной единице. Первый подтверждается, второй получает `409`; итоговые значения `onHand = 1`, `reserved = 1`, `available = 0`. Повторить с двумя параллельными запросами и с повторным подтверждением одного заказа.

**Затронуто:** подтверждение заказов, складской резерв, конкурентные операции.

**Коммит:** `bd0390bc3c5a4dc0537f3072937398c64bcf310f`.

## QA-104 — Устаревший статус в списке заказов

**Причина.** После успешной мутации TanStack Query обновлял кеш отдельного заказа через `setQueryData(orderKey(id), order)`, но не обновлял кеш списка.

**Исправление.** После успешного действия инвалидируется ключ списка заказов (`ordersKey`), что вызывает повторное получение актуальных данных для активного запроса. Кеш карточки заказа по-прежнему обновляется непосредственно из ответа сервера.

**Проверка.** В списке нажать «Подтвердить» или «Отменить»; убедиться, что статус и доступные кнопки меняются без F5. Проверить, что повторное ошибочное действие не предлагается интерфейсом.

**Затронуто:** список заказов, кеш TanStack Query.

**Коммит:** _вписать новый хеш после разделения коммитов_.

## QA-105 — Отмена уже отгруженного заказа

**Причина.** Отмена снимала резерв для любого статуса, кроме `DRAFT`, включая `SHIPPED`, хотя при отгрузке резерв уже был снят. Это приводило к отрицательному `reserved`.

**Исправление.** Отмена отгруженного заказа запрещается с ответом `409`; резерв освобождается только для `CONFIRMED`. Для предотвращения двойного освобождения при параллельных запросах переход статуса следует выполнять условно в одной транзакции. Отгрузку также необходимо защищать от гонки с отменой.

**Проверка.** Создать заказ на 2 единицы → подтвердить → отгрузить → попытаться отменить. Ожидать `409`, сохранение статуса `SHIPPED`, `reserved = 0` и корректный `onHand`. Отдельно проверить повторную и конкурентную отмену подтверждённого заказа.

**Затронуто:** отмена, отгрузка, складские остатки.

**Коммит:** fbf9124f8144b870703840654a96529e22f980eb.
